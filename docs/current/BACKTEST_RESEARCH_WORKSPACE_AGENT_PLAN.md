# Research Workspace: 에이전트 설계 검토와 구현 계획

작성: 2026-09-10. 상태: 구현 전 설계. 검토 기준: 로컬 `feat/backtest-mvp-v1`, `fbdb44f`.

사용자가 선택한 범위는 **전략 파라미터 편집 + 제한된 신호 수식 편집**이다. 목표는 사용자가 가설을 만들고, 설정을 바꾸고, 같은 표본에서 비교하고, 유망한 실험을 보관하는 연구 작업 공간이다. 현재 10분 표본으로 이 작업 흐름을 완성한다. 표본 내 탐색 결과와 paper trading 적격성은 별도 상태로 관리한다.

이 문서는 실행 코드 변경 또는 에이전트 작업 시작을 의미하지 않는다.

## 1. 현 구현에 대한 판정

| 확인한 코드 | 문제와 영향 | 조치 |
|---|---|---|
| `research.py:make_plan`, `run_research` | `DEFAULT_SETTINGS`가 입력값을 덮어쓴다. 사용자가 수정한 설정을 실험한다는 계약과 맞지 않는다. | 새 작업 공간은 기본값을 초안 생성 때만 사용한다. 최종 설정 미리보기와 실행 입력을 동일 객체에서 만든다. |
| `research.py:SCENARIOS`, `evaluate` | 고정 6개 시나리오와 승격 판정이 실험 설계를 지배한다. | 전략 파라미터 축과 체결·비용 시나리오를 분리한다. 기존 연구는 명시적인 호환 프리셋으로 보존한다. |
| `research_ui.py:render_research` | 화면에서 동기 실행하며, 설정 편집·복제보다 승격 차단이 앞선다. | 초안 → 실행 미리보기 → 작업 진행 → 비교 → 복제를 주 흐름으로 만든다. |
| `runner.py:_RUN_LOCK` | `threading.Lock`은 프로세스 간 UI/CLI 실행을 조정하지 못한다. | 기존 VM에서 UI·CLI가 공유하는 OS 파일 잠금과 별도 worker를 사용한다. |
| `MarketView`, `PortfolioView`, `StrategyParameters` | 관측 정보와 체결 내부 상태를 분리할 기반이 있다. | 이 경계를 유지하고 수식에도 명시적으로 허용된 스칼라만 전달한다. |

기존 재구성, 체결, 회계, 기록 및 회귀 테스트를 재사용한다. 이 검토는 전체 엔진의 정확성을 새로 인증한 결과가 아니다. 기존 테스트 통과 기록과 이번 변경의 검증 결과를 구분한다.

## 2. 에이전트 구성과 검토 규칙

총괄 1명과 전문 에이전트 3명, 최대 4개 동시 작업으로 구성한다. 역할 수보다 책임 경계와 독립적인 검증 증거가 중요하다. 구현자는 자신의 단위 테스트를 작성하고, QA는 별도의 기대값과 반례를 작성한다.

| 담당 | 책임 / 산출물 | 코드 소유 범위 | 독립 검토 상대 |
|---|---|---|---|
| Root: 제품 계약·통합 | 사용자 작업 흐름, 타입·상태 계약, 변경 승인, 통합 및 완료 판정 | 공통 계약, 기존 앱·설정·runner 연결부, 의존성·문서 | QA의 증거로 통합 판정; UI/엔진 간 계약 충돌 해결 |
| A: 연구 UX | 편집, 수식 도움말, 실행 미리보기, 작업 상태, 결과·복제·이력 | 새 `workspace_ui/` 모듈과 UI 단위 테스트 | B가 표시값과 실제 입력 대조; C가 사용자 시나리오 검증 |
| B: 실험 시스템 | 수식 실행, 설정 해석, 그리드, 작업 저장·중단·재개, 결과 조회 | 새 `workspace/` 구현, 수식 어댑터, 엔진의 필요한 취소 hook | C가 인과성·결정성·회계·장애 사례 검증 |
| C: 독립 QA | 요구사항 추적표, 수작업 기대값, 적대적 사례, CLI/UI 대조, Linux 검증 | 독립 `tests/backtest/workspace_acceptance/`, 검증 스크립트·증거 | Root가 재현 확인; A/B가 수정 후 C가 재검증 |

운영 규칙:

- 시작할 때 기준 commit, 표본 checksum, 요구사항 버전, 파일 소유권을 공유한다. 동일 파일의 동시 수정은 금지한다. 공통 파일 변경은 Root가 통합하거나 한 담당자에게 시간 구간을 정해 배정한다.
- QA는 사용자 요구와 공개 계약을 먼저 읽고 기대 동작을 작성한다. 초기 판정 전에는 구현자의 성공 설명을 근거로 사용하지 않는다. 재현에 필요한 소스·도구 접근은 제한하지 않는다.
- 발견 사항은 `요구사항 ID / 심각도 / 재현 입력 / 기대값 / 관측값 / 증거 / 담당 / 상태`로 기록한다. 합의나 다수결로 닫지 않는다.
- 잘못된 체결·손익, 미래 정보 접근, 설정 유실, 중복 실행, 이력 손실은 출시 차단 사항이다. 핵심 사용자 흐름을 막는 UI 문제도 해결 후 통합한다.
- 반론은 fixture 또는 사용자 흐름의 재현으로 해결한다. 두 번의 수정·재검증 후에도 이견이 남으면 Root가 최소 재현으로 계약을 명확히 하고 작업 범위를 조정한다. 미해결 문제를 승인 처리하지 않는다.
- 에이전트는 임의로 모델 가정·수수료·데이터 구간을 바꿔 성과를 개선하지 않는다. 실제 발견한 실패는 `docs/internal/FAILURES.md`와 해당 검토 기록에 남긴다.
- 에이전트 간 합의는 독립된 시장 검증을 대신하지 않는다. 별도의 기간과 실거래 관측 자료가 필요한 항목은 근거 부족 상태로 유지한다.

### 첫 작업 배정문

**A:** 현 UI에서 ‘한 설정 수정 → 실행 → 결과 복제’를 따라가며 혼동과 단절을 기록한다. 새 화면의 낮은 정밀도 시안, 필드·상태 목록, 빈 결과·실패·중단 화면을 제출한다. 엔진 코드는 수정하지 않는다.

**B:** 현재 입력이 `BacktestConfig`와 engine까지 전달되는 경로를 추적한다. 덮어쓰기 위치, 해시 대상, worker 및 취소 hook 위치, 기존 회귀 계약을 제출한다. 첫 구현 단위는 단일 초안의 정확한 실행이다.

**C:** 아래 R01–R12를 구현 설명과 독립적으로 테스트 사례로 구체화한다. Decimal 손익 기대값, 설정 전달, 수식 접근 제한, 중단 후 재개 사례를 우선 작성한다. 제품 코드의 실패를 테스트 완화로 해결하지 않는다.

**Root:** 세 검토와 병행해 아래 공통 계약 및 파일 소유권을 고정한다. 먼저 한 개 설정을 끝까지 실행하는 작은 통합본을 만든 뒤 다음 단계를 연다.

## 3. 제품 흐름과 공통 계약

주 화면은 `전략 편집 / 실험 실행 / 결과 비교 / 연구 이력`으로 구성한다. 모델 가정, 수식 의미, 단위를 해당 입력 옆에서 설명한다. 기존 주문·체결·원장 화면은 결과에서 바로 연결한다. 기존 연구 기능과 과거 아티팩트는 읽기 및 재현 경로를 유지한다.

1. 기존 전략 또는 신호 수식 템플릿을 선택하고 이름·가설을 입력한다.
2. 단일 값 또는 탐색 범위를 편집한다. 전략, 위험 정책, 체결·비용 가정을 구분해 표시한다.
3. 실행 수, 실제 적용값, 기준값과의 차이, 표본·코드 지문을 확인한다.
4. 명시적인 제출로 설정을 동결하고 실행한다. 화면 이동·재실행은 새 작업을 제출하지 않는다.
5. 동일 조건의 결과를 정렬·필터링하고 곡선·히트맵·체결 근거를 확인한다.
6. 결과를 복제해 새 초안을 만들고 한 가지 가설을 수정한다. 원본 결과와 부모 관계를 보존한다.
7. 즐겨찾기·노트와 함께 탐색 후보를 저장한다. paper 적격성은 결과와 구분해서 표시한다.

| 계약 | 필수 내용 | 변경 규칙 |
|---|---|---|
| `StrategyDraft` | ID·revision·부모 실행, 이름·가설, 내장 전략 또는 수식, 파라미터 정의·값, 위험 정책, 실행 가정 | 편집 가능. 저장 때 revision 검사로 다른 탭의 편집을 조용히 덮어쓰지 않는다. |
| `ExperimentSpec` | schema version, 동결한 draft revision, 표본·코드 지문, 탐색 축, 시나리오 패치, 모든 최종 실행 설정 | 제출 후 불변. 미리보기와 worker가 동일 설정 목록을 소비한다. |
| `ResolvedRunSpec` | variant ID, 정확한 엔진 설정, 수식·언어 버전, 위험/헤지 정책, 각 값의 출처, effective hash | Decimal은 문자열로 보존한다. 코드·표본·정책을 포함한 실행 식별자를 사용한다. |
| `JobState` | job ID, 실행 상태, 현재 variant, 시도 번호, 완료/실패/미실행 개수, 취소 요청 | 원자적 교체로 저장한다. 완료 결과와 작업 진행 기록을 분리한다. |
| `SimulationRun` | 실행 명세, 상태, 결정적 digest, 요약·불변식, 아티팩트 위치·checksum | 완료 실행은 수정하지 않는다. 실패·중단 재시도는 새 attempt로 남긴다. |
| `ComparisonSpec` | 선택한 실행 ID, 비교 축, 고정 조건, 정렬·필터, 표본 일치 검사 | 그래프의 집계 조건까지 저장한다. 서로 다른 가정을 한 전략 점수로 조용히 섞지 않는다. |

의존 방향은 `UI/CLI → workspace 서비스 → 기존 runner/engine`이다. 엔진은 Streamlit을 import하지 않는다. 순수 `resolve_experiment`가 전체 설정 검증·축 전개·해시 생성을 담당한다. UI와 CLI에 별도의 설정 조립 로직을 만들지 않는다.

공유 파일 제안:

- `backtest/workspace/contracts.py`: Root 소유, 버전이 있는 계약.
- `backtest/workspace/resolve.py`, `expressions.py`, `store.py`, `jobs.py`, `worker.py`, `compare.py`: B 소유.
- `backtest/workspace_ui/editor.py`, `experiments.py`, `results.py`, `history.py`: A 소유.
- `config/backtest.py`, `strategies.py`, `runner.py`, `engine.py`, `arrival.py`, `apps/backtest_lab.py`: Root가 변경 위치를 배정하고 통합한다.
- 독립 acceptance 테스트와 `scripts/validate_backtest_workspace.py`: C 소유. A/B 단위 테스트 디렉터리와 분리한다.

## 4. 제한된 신호 수식의 명세

첫 버전의 수식 출력은 **호가 중심 이동량(ticks)** 하나다. 반스프레드·주문량·재고 한도 등은 별도의 편집 가능한 파라미터이며 탐색 축으로 사용할 수 있다. 매수·매도 주문 생성, tick/lot 반올림, post-only, 위험 통제, 취소·체결 처리는 기존 경로를 공유한다.

```text
signal_strength * (microprice - mid) / tick
    - inventory_skew_ticks * inventory / max_inventory

center = mid + tick * expression_result
```

에디터에는 가격 단위와 ticks 단위를 구분한 예제, 변수 사전, 알려진 관측값으로 계산하는 미리보기를 제공한다. 미리보기의 샘플 값은 실제 성과로 표시하지 않는다.

- 허용 입력: `bid`, `ask`, `mid`, `microprice`, `tick`, `imbalance`, `spread_ticks`, `volatility_bps`, `trade_imbalance`, `trade_volume`, `inventory`, `max_inventory` 및 선언된 Decimal 파라미터.
- 각 변수의 관측 시점·단위·결측 조건을 명세한다. recorded clock에서는 client에 전달된 market/portfolio 상태만 사용한다. 과거 창은 기존 1초 거래 흐름과 30초 변동성으로 고정하고 버전을 기록한다.
- 허용 문법: 숫자 리터럴, 이름, 괄호, `+ - * /`, 단항 부호, `abs/min/max/clip`. 직접 AST를 검증하고 평가한다. `eval`, `exec`, import, attribute 접근, indexing, 임의 함수 호출, 루프, 파일·네트워크 접근은 없다.
- 체결 alpha, queue, future event, replay iterator, 실제 exchange 재고, 엔진 객체는 입력으로 제공하지 않는다. 파라미터 이름이 예약된 관측 변수를 덮어쓰면 거부한다.
- 파라미터 값과 숫자 리터럴은 Decimal로 해석한다. 기존 float 변동성의 Decimal 변환 규칙은 고정한다. 수식 문자열·언어 버전·파라미터·효과적 설정을 모두 저장한다.
- 초기 제한: 수식 길이 1,000자, AST 노드 128개, 깊이 16, 숫자 리터럴 유효숫자 28자리. 비유한 값과 표현 범위를 벗어난 결과는 오류로 처리한다. 정책 범위를 벗어난 중심 이동은 사전 설정한 `max_signal_ticks`에 의해 잘리고 clipping 횟수를 기록한다.
- `max_signal_ticks` 초기값은 10 ticks, 사용자가 명시적으로 수정 가능하다. 잘라낸 신호와 위험 통제로 억제된 호가를 구분해서 보여준다.
- 필요한 관측값이 결측이면 `feature_unavailable`로 신규 호가를 억제하고 기존 취소 규칙을 따른다. 0으로 나누기 등 수식 실행 오류는 실패 상태와 마지막 정상 증거를 저장하고 해당 실행을 중단한다. 실패 결과를 정상 10분 성과로 집계하지 않는다.
- 미래 접미부 변경 테스트와 손계산 수식 예제로 인과성과 의미를 검증한다. 내장 microprice·inventory skew에 대응하는 수식이 같은 주문을 내는 parity 사례를 둔다.

## 5. 탐색, 작업 실행과 이력

### 설정 및 그리드

기본값은 신규 초안을 만들 때만 채운다. 이전 고정 연구값은 이름 붙은 프리셋으로 제공한다. 기존 결과 복제는 그 결과에 저장된 설정을 그대로 가져온다. 위험·헤지 정책도 저장·표시·해시 대상이며 runner 내부에서 새 기본값으로 바꾸지 않는다.

탐색 축은 명시적 값 목록 또는 시작/끝/간격이다. Decimal로 전개하고 정규화한 중복값을 제거한다. 사용자가 결과를 미리 볼 수 있도록 최종 목록과 제거된 중복을 표시한다. 잘못된 조합이 하나라도 있으면 제출 전에 설명하고 수정하게 한다. 몰래 제외하지 않는다.

전략 축과 실행 시나리오는 별도로 선택한다. 시나리오는 fill mode/alpha, clock/latency, fees, 이미 구현된 비용 스트레스 항목만 패치한다. 같은 필드를 축과 시나리오 양쪽에서 지정하면 모호성 오류로 거부한다. 정책 변경은 명시적인 정책 축으로 표시한다.

첫 릴리스는 기존 운영 제한을 유지해 **제출당 최대 24개, 동시 worker 1개**로 한다. 기본은 실행 가정 1개다. 예를 들어 반스프레드 3 × skew 3 = 9개를 먼저 실행하고, 선택한 결과를 비용 시나리오에 보낼 수 있다. 24개 초과는 정확한 개수와 분할 방법을 보여주고 제출을 차단한다. 앞의 24개만 실행하지 않는다. 계약에는 제한값을 박아 넣지 않아 향후 측정 후 확장할 수 있게 한다.

전략 ID와 시나리오 ID를 별도로 유지한다. 탐색 기본 표는 하나의 기준 시나리오에서만 정렬한다. 시나리오 민감도 표는 같은 전략 설정에 대해서만 구성하고 누락된 셀을 명시한다. 낙관적 fill assumption을 ‘최적 전략 파라미터’로 선정하지 않는다.

### 실행과 중단

Streamlit은 초안을 저장하고 작업을 제출·조회한다. 유한 수명의 별도 Python worker가 기존 Ubuntu에서 순차 실행한다. 새 서비스, DB, broker, 공개 포트는 추가하지 않는다.

상태는 `QUEUED → RUNNING → COMPLETED | FAILED | CANCELED | INTERRUPTED`이다. 취소 요청은 별도 `cancel_requested` 필드다. 실행 상태와 표본 내 성과·paper 적격성을 서로 다른 필드로 보관한다.

- 제출 키와 동결된 설정으로 UI 재실행·더블 클릭의 중복 제출을 막는다. 동일 설정 재실험은 명시적인 ‘다시 실행’으로 새 job을 생성한다.
- worker 시작 시 UI·CLI·기존 runner 모두 같은 OS 파일 잠금을 획득한다. 큐는 작성 시각+ID 순으로 처리한다. 잠금 경쟁에 진 worker는 즉시 종료한다. 프로세스 종료 시 잠금이 해제되어야 한다.
- worker는 job의 완료 상태·파일 checksum을 확인하고 다음 미완료 variant부터 시작한다. 모든 실행은 새 portfolio/order/feature 상태로 생성한다.
- 취소는 시장 timestamp 그룹 사이의 안전한 경계에서 확인한다. 취소 요청으로 계산을 멈추며, 모델상 강제 청산이나 가상의 취소 체결을 만들지 않는다. 중단 시각과 미해결 주문·재고를 저장한다.
- UI는 현재 variant와 완료 개수를 polling해 보여준다. 화면 전환과 브라우저 종료는 worker를 중단하지 않는다. app 재연결 시 저장된 상태를 복구한다.
- 프로세스 사망은 PID만으로 판단하지 않고 잠금 소유 여부·worker 식별 정보로 확인한다. 남은 RUNNING job을 INTERRUPTED로 표시한다. 단순 heartbeat 지연으로 생존 worker를 재실행하지 않는다.
- 재개는 완료 variant를 checksum 확인 후 재사용한다. 진행 중이던 variant는 처음부터 새 attempt로 실행한다. 과거 attempt를 삭제하지 않는다. 코드·표본·설정이 달라졌으면 재개를 거부하고 새 실험으로 복제한다.
- 실패한 variant가 발생하면 후속 실행을 일단 멈추고 실패 증거를 남긴다. 재개 이후에도 일부 실패가 있는 작업을 전체 완료로 표시하지 않는다.

새 저장 경로는 `artifacts/backtest/workspace/` 아래 drafts, experiments, jobs, reviews이며 개별 실행 증거는 기존 run artifact 계약을 재사용한다. mutable 메타데이터와 immutable 실행 결과를 구분한다. 기존 research/runs는 migration 없이 읽는 어댑터를 제공한다. 출처 필드가 없는 과거 결과는 새 값으로 추정해서 채우지 않는다.

## 6. 결과 분석과 후보 저장

결과에는 순/총손익, maker/taker 비용, spread capture·inventory MTM, 재고, drawdown, 주문·체결 수, markout coverage, 위험 중단 및 잔여 재고를 표시한다. 실행 활성화 시간, 체결 0건, 수식 결측/오류/clipping, 위험 통제 사유를 손익 옆에서 확인할 수 있어야 한다.

두 축은 히트맵으로, 더 많은 축은 나머지 값을 고정한 slice로 보여준다. 고정하지 않은 축을 평균내어 숨기지 않는다. 기준 대비 차이와 인접 파라미터 성과를 확인하고, 순손익·낙폭·재고 사용량의 trade-off를 비교한다. 기본 순손익 정렬은 ‘이 표본의 정렬’로 명시하며 임의의 종합 점수를 만들지 않는다.

10분 표본을 반복 탐색한 횟수와 동일 표본 재사용 사실을 이력에 남긴다. 체결 1건 전략과 충분히 활동한 전략은 체결량과 가동률을 함께 비교한다. 최소 체결 수 등 필터는 편집 가능하고 필터 조건을 저장한다. 10분 결과에 Sharpe나 통계적 유의성·확률 보장을 추가하지 않는다.

‘탐색 후보 저장’은 허용한다. 별도 상태 `paper_eligibility=INSUFFICIENT_EVIDENCE`와 부족한 근거를 표시한다. 계정 연결·실주문·paper 자동 시작은 이번 범위에 없다. 마켓임팩트와 queue 추정값은 관측 진실 또는 보정 완료로 표기하지 않는다.

UI·worker 합산 메모리도 기록해 worker 수치만으로 VM 여유를 판단하지 않는다.

## 9. 구현 환경과 변경 범위

구현은 현재 로컬 커밋을 기준으로 별도 feature branch/worktree에서 진행한다. 기존 Ubuntu 앱 checkout에 미커밋 변경이 남아 있는 이력이 있으므로 구현 시작 때 read-only 상태를 다시 확인하고 별도 checkout에 준비한다. 기존 runtime을 restore/reset하거나 그 위에 덮어써 동기화하지 않는다. 검증을 통과한 뒤 app checkout 전환은 별도로 계획한다.

이번 범위에는 새 데이터 수집, 다른 표본 선택, queue 진실 복원, 마켓임팩트 보정, funding/증거금 모델 확장, 자동 전략 최적화·ML, 실제 paper/live 주문, 공개 배포, 새 인프라가 포함되지 않는다. 필요한 엔진 오류는 재현 증거를 붙여 수정하되 전략 성과를 이유로 체결 가정을 바꾸지 않는다.
