# 주요 의사결정 기록

각 항목은 "무엇을 정했나 / 왜 / 무엇을 포기했나" 순서. 나중에 다시 논의될 때
같은 자리를 두 번 파지 않기 위한 문서.

## D1. FPGA를 어디에 쓸 것인가

**결정: 피드 핸들러 / 호가창 빌더. 전략 로직에는 쓰지 않는다.**

### 근거

FPGA 보드를 다룰 수 있는 팀원이 있으나 "실제 트레이딩에 안 쓰면 의미 없지 않나"는
고민이 있었다. 결론은 **실전 경로에 넣는 건 실제로 의미가 없지만, 그게 FPGA를
쓰지 말아야 할 이유는 아니다**.

- 크립토 거래소는 TLS + WebSocket이고 왕복 지연이 수십 ms다.
  보드에서 수백 ns를 줄여도 네트워크 노이즈에 묻힌다. → 실전 주문 경로에 FPGA는 무의미.
- **그런데 실제 HFT/MM 회사도 FPGA로 전략을 돌리지 않는다.** FPGA가 쓰이는 곳은 셋뿐:
  1. 피드 핸들러 / 북 빌더 (바이너리 시세 파싱 → 북 재구성 → top-of-book 출력)
  2. Pre-trade risk check (포지션 한도, 주문 크기, kill switch)
  3. 주문 게이트웨이
- 즉 **실전과 똑같은 역할 분담을 리플레이 환경에서 재현**하면 된다.
  이건 업계 표준 아키텍처라 리쥬메에 그대로 적힌다.

### 구체적 역할

- **메인**: 하드웨어 호가창 빌더 (F1) + 소프트웨어 참조 구현과 bit-exact 검증 (F2)
- **핵심 기여**: Phase 3의 레이턴시 축을 **가정이 아닌 실측값**으로 바꾼다.
  Python / C++ / FPGA 세 경로의 tick-to-trade를 측정해 분포로 주입.
- **스트레치**: 하드웨어 pre-trade risk check (F4)
- **하지 않음**: 주문 게이트웨이, 전략 로직

### 포기한 것

"FPGA로 실시간 트레이딩하는 프로젝트"라는 그림. 대신 얻은 것은 정직함이다.
면접에서 "FPGA를 왜 썼나, 실전에 쓸 수 있나"를 물으면
**"전략이 아니라 피드 핸들러에 썼고, 크립토에서는 처리 지연이 네트워크 지연에
묻힌다는 걸 실측으로 보였다"**고 답할 수 있다. 이 답이 오히려 강점이다.

### 운영 원칙

**FPGA 트랙은 크리티컬 패스에 두지 않는다.** 소프트웨어 시뮬레이터가 없으면 FPGA는
검증 대상이 없고, FPGA가 늦어져도 프로젝트는 완성되어야 한다.
병렬 트랙으로 두고 **인터페이스(LOBMSG 포맷)만 2주차에 고정**한다.

## D2. 어느 시장에서 할 것인가 — 크립토 vs 국내 주식

**결정: 크립토가 본체. 국내 주식은 별도의 작은 관측 연구 모듈(스트레치).**

### 국내 주식의 구조적 제약 네 가지

1. **L3가 없고 10호가뿐이다.** 토스든 한투든 KRX 실시간 시세는 10단계 호가 잔량이다.
   큐 위치는 여전히 관측 불가고, Binance보다 오히려 깊이가 얕다. 게다가 국내 실시간
   호가는 증분(diff)이 아니라 10호가 전체 스냅샷이라 그 사이 개별 변화가 뭉개진다.
2. **데이터가 하루 6.5시간이다.** (KRX 09:00~15:30) 크립토는 24시간.
   같은 3개월을 모아도 표본이 4배 차이. MM처럼 체결 이벤트 수가 곧 검정력인
   연구에서 이건 크다.
3. **라이브 검증(Phase 5)이 원리적으로 불가능하다.** ★ 가장 결정적
   마켓메이킹은 재고가 음수가 될 수 있어야 성립하는데 개인은 공매도를 자유롭게 못 한다.
   양방향 호가를 낼 수가 없다. 시뮬레이션은 "LP 라이선스가 있다고 가정"하면 되지만,
   **페이퍼 트레이딩으로 백테스트 vs 현실 괴리를 검증하는 단계는 못 한다.**
4. **토스 API가 너무 새것이다.** 정식 서비스가 2026년 8월 13일. 문서·레이트리밋·안정성이
   미검증. 국내 데이터를 꼭 쓴다면 **한국투자증권 KIS API**가 낫다
   (`python-kis`, 공식 `open-trading-api` 레포 등 커뮤니티 성숙).

### 그럼에도 국내에 좋은 게 하나 있다 — NXT

2025년 3월 넥스트레이드 출범으로 **같은 종목이 KRX와 NXT 두 거래소에서 동시 거래**된다.
2025년 8월 기준 NXT 점유율이 거래대금 기준 31.9%. 중간가호가·SOR·최선집행의무가 다 붙어 있다.

이건 구조적으로 **ETF LP 문제와 같다.** 두 개의 가격 발견 장소, 그 사이의 괴리,
어디에 호가를 내고 어디서 청산할지.

그리고 **국내 증권사 면접에서 압도적으로 유리한 소재**다. ETF LP 데스크가 지금 실무로
다루는 문제이기 때문이다.

### 국내 모듈 설계 (스트레치, 2~3주)

백테스트가 아니라 **미시구조 실증 연구**다. 관측만 하므로 공매도 제약도 큐 위치 문제도
안 걸린다.

- KIS API로 KRX + NXT 동일 종목 10호가·체결 동시 수집 (삼성전자, 대형 ETF 몇 개)
- 두 거래소의 스프레드·깊이·체결 분포 비교
- 가격 발견 선도성 (리드-래그, 정보 점유율)
- 중간가호가가 유효 스프레드에 미치는 영향
- ETF에서 KRX-NXT 괴리와 iNAV 대비 프리미엄 관계

**우선순위는 낮게.** 이미 FPGA + 크립토 MM + 헤지로 트랙이 셋이다.
네 번째를 넣으면 다 얕아진다. Phase 0~3이 안정적으로 끝난 뒤 여유가 있으면 붙인다.

## D3. 크립토 어느 거래소에서 실주문까지 할 것인가

**결정: 데이터는 Binance 공개 시세, 실주문은 하지 않거나 업비트 소액.**

| 갈래 | 판정 | 이유 |
|---|---|---|
| 국내 거래소 (업비트·빗썸) | 실주문 O, 수익 X | 업비트 0.05% / 빗썸 0.04% 고정 수수료, 메이커 구분 없음. BTC/KRW 스프레드는 대부분 1틱(0.001% 미만) → 순수 MM 불가. **단 큐 모델 캘리브레이션·레이턴시 실측에는 충분** |
| 해외 거래소 (Binance 등) | 시세 O, 실주문 X | 메이커 0.02%로 MM 경제성은 성립하나, 2026년 1월 구글이 미신고 가상자산 앱을 전면 차단하는 등 접근이 회색지대. **컴플라이언스 관점에서 "미신고 거래소 실거래" 흔적은 리쥬메에 마이너스** |
| 테스트넷 | 시스템 검증용 | 유동성이 가짜라 역선택·큐 검증에는 무의미 |

**주의:** 업비트에서 양방향 호가를 낼 때 자기 매수·매도가 서로 체결되는 자전거래는
시장교란으로 볼 수 있다. **자기 체결 방지 로직 필수.**

## D4. Binance 직접 수집 vs Tardis.dev 구매

**결정: 둘 다. 단 역할이 완전히 다르다. Binance가 8, Tardis가 2.**

| | Binance 직접 수집 | Tardis Coinbase L3 |
|---|---|---|
| 역할 | **프로젝트 본체** | **Phase 0.5 전용** |
| 기간 | 무제한, 연속 3개월+ | 매월 1일만, 총 ~90일 |
| 비용 | 무료 (VPS만) | 무료 (무료 구간 내) |
| 쓰는 곳 | Phase 0~5 전부 | 큐 모델 캘리브레이션 한 번 |

### Binance가 본체인 이유

1. **연속성.** MM 백테스트는 연속 기간이 필요하다. 재고가 쌓이고 풀리는 과정,
   변동성 국면 전환, 일중 패턴이 다 시간 연속성 위에서 나온다.
   매월 1일만 있는 데이터로는 Phase 1~4를 못 돌린다.
2. **수집기를 직접 만드는 것 자체가 산출물이다.** 시퀀스 갭 처리, 재동기화,
   24시간 무중단 운영, 품질 검증 — Tardis에서 받아쓰면 이 경험이 안 생긴다.
   면접에서 "데이터는 어디서 구했나요"에 "샀습니다"와 "직접 수집했습니다"는
   후속 질문의 깊이가 다르다. FPGA에 넣을 LOBMSG도 본인 파이프라인에서 나와야 한다.
3. **Tardis 유료는 학생 팀에 부담.** Binance 직접 수집은 VPS 무료면 끝.

### Tardis는 딱 한 가지에만

Coinbase L3 큐 정답 연구. Binance로는 **원리적으로 불가능**하고(L2만 주니까),
90일이면 충분하다. 큐 캘리브레이션은 연속성이 필요 없고 서로 다른 국면의 표본 수만
있으면 되기 때문.

### 보너스 — 내 수집기 검증

Tardis는 **Binance 데이터도** 매월 1일 무료로 준다. 같은 날짜를 내 수집기와 Tardis
양쪽에서 확보해 메시지 수, 시퀀스 갭, 재구성된 top-of-book을 비교하면
**내 수집기가 전문 업체 캡처와 얼마나 일치하는지** 검증할 수 있다.
비용 0원인데 "데이터 품질을 어떻게 담보했나"에 바로 답이 된다.

## D5. Coinbase L3에 어떻게 접근할 것인가

**결정: Coinbase 직접 연결은 포기. Tardis.dev 무료 구간을 쓴다.**

### Coinbase가 특별한 이유

`full` 채널은 주문 생애주기 전체를 개별 주문 단위로 준다.

| 메시지 | 의미 |
|---|---|
| `open` | 주문 북 등재 — **여기서 큐 순위 확정** |
| `match` | 체결. `maker_order_id`로 **어느 주문이 체결됐는지 특정** |
| `done` | 종료. `filled` vs `canceled` **구분됨** |
| `change` | 수량 감소 (우선순위 유지) |

price-time priority FIFO이므로 **`open` 도착 순서 = 큐 순서.**
따라서 시각 t에 가격 p로 주문을 냈다면 내 앞에 어떤 주문이 있었고 그것들이
체결됐는지 취소됐는지, 내 주문이 언제 체결됐을지를 **정확히 계산**할 수 있다.

Binance/업비트 L2로는 원리적으로 불가능하다. 레벨 잔량이 100→80으로 줄었을 때
20이 체결인지 취소인지, 내 앞인지 뒤인지 알 수 없다.

### 왜 직접 연결은 안 되나

`full`, `level3`, `level2` 채널 모두 **인증 필요**. 그 인증은 **기관용
Coinbase Exchange 계정**(exchange.coinbase.com)을 요구한다. 리테일 Advanced Trade
계정으로는 발급되지 않는다. Coinbase Pro는 2023년 12월 종료되어 기존 무인증 경로도 막혔다.

**개인은 불가능하다. 이 길은 완전히 포기하는 게 맞다.**

### Tardis 무료 경로

- Coinbase Exchange 데이터 **2019-03-30부터** 아카이빙
- 캡처 채널: `received`, `open`, `done`, `change`, `match`, `full_snapshot`
- **API 키 없이 매월 1일 데이터 접근 가능** → 2019-03 ~ 2026-09 = **약 90일 무료**

**주의 2가지**
1. `download_datasets()`(CSV)는 **정규화된 L2만** 준다.
   L3를 받으려면 반드시 `replay()`(exchange-native)를 써야 한다.
2. Tardis 문서에 **Coinbase 시장데이터 라이선스 제한**이 적용된다고 명시.
   포트폴리오 공개 시 파생 결과(통계·그래프)만 올리고 원본은 재배포하지 말 것. 코드는 무방.

### 이미 나온 성과

`code/l3_queue.py` 테스트에서 **앞 물량 8 중 5는 체결, 3은 취소**되어 실제로는
체결됐는데 비관 모드는 "체결 안 됨"으로 예측했다.

**"비관 = 보수적 = 안전"이라는 전제가 틀렸다.** 취소가 많은 시장에서는 체결을 놓치는
방향으로 틀리고, MM 전략의 수익 기회를 과소평가한다. L3 없이는 알 수 없던 사실이고,
이것 하나로 Phase 0.5의 값을 한다.

## D6. 서버를 어디에 둘 것인가

**결정: Oracle Cloud Always Free, 홈 리전은 도쿄(차선: 서울).**

### ⚠️ 가장 중요한 함정

**Binance는 미국 IP를 공개 시세 API까지 451로 차단한다.**
2022년 11월부터 인증 없는 read-only 엔드포인트도 막혔다.
Restricted Location에 미국, 말레이시아, 캐나다 온타리오 등이 포함된다.

→ **Google Cloud 무료 티어(e2-micro)는 us-west1/central1/east1 만 제공하므로 사용 불가.**
무료 티어 중 가장 유명한 선택지가 여기서 탈락한다. PythonAnywhere 등 미국 호스팅도 동일.

### 옵션 비교

| 옵션 | 판정 | 이유 |
|---|---|---|
| **Oracle Cloud Always Free** | **채택** | 도쿄/서울 리전, 200GB, 영구 무료 |
| Google Cloud 무료 | 불가 | 미국 리전만 → 451 |
| AWS 무료 | 부적합 | 2025년부터 크레딧 방식, 영구 아님 |
| Fly.io / Railway / Render | 부적합 | 스토리지 휘발성, 슬립 |
| 집 PC / 라즈베리파이 | 백업안 | 정전·인터넷 끊김으로 구멍 |

### Oracle 현재 제공량 (2026-09 기준)

2026년 6월 15일부로 ARM 할당량이 **공지 없이 반토막**났다.

| 자원 | 이전 | 현재 |
|---|---|---|
| Ampere A1 (ARM) | 4 OCPU / 24GB | **2 OCPU / 12GB** |
| AMD 마이크로 | 2 × (1/8 OCPU / 1GB) | 변동 없음 |
| 블록 스토리지 | 200GB | **변동 없음** |

**수집기에는 2 OCPU / 12GB로 차고 넘친다.** 스토리지가 그대로인 게 핵심.
ARM 용량 부족("Out of host capacity")이면 AMD 마이크로로도 충분히 돌아간다.

### 놓치면 안 되는 것

- **홈 리전은 가입 시 정해지고 변경 불가.** 실수로 US를 고르면 계정 재생성밖에 없다.
- 블록 볼륨은 **Lower Cost** 선택 (Balanced는 유료)
- `/etc/fstab`에 `nofail` 필수 (볼륨 미부착 시 부팅 멈춤 방지)
- **무료 티어는 언제든 정책이 바뀐다.** 데이터를 서버에만 두지 말 것 (rclone 백업)
- 알림은 **서버 밖에서** 걸어야 한다. 서버가 죽으면 서버발 알림도 같이 죽는다
  → Healthchecks.io 같은 dead man's switch

## D7. Phase 4를 무엇으로 할 것인가

**결정: 시그널 스큐 → 페어밸류 기반 호가 + 크로스 거래소 헤지로 교체.**

### 근거

원래 Phase 4는 "단기 예측을 호가 스큐의 입력으로 쓰기"였는데, 예측 색이 있어
ETF LP와는 거리가 있었다.

ETF LP의 본질은 **"헤지 가능한 상품을 페어밸류 대비 호가하고 재고를 헤지하는 것"**이다.
이걸 크립토로 축소하면:

| 역할 | ETF LP 실제 | 이 프로젝트 |
|---|---|---|
| 호가 대상 | ETF | 거래소 A (유동성 낮은 곳) |
| 페어밸류 원천 | 바스켓 / 지수선물 / iNAV | 거래소 B (바이낸스) 미드 또는 perp |
| 헤지 수단 | 선물 / 바스켓 매매 | 거래소 B perp 또는 spot |
| 괴리 요인 | 프리미엄/디스카운트, 환율, 배당 | 거래소 간 베이시스, 펀딩비 |

손익 분해에 **헤지 비용** 항목이 하나 추가되는 구조라 기존 회계 틀과 자연스럽게 맞는다.

**기대 결과:** 헤지로 재고 손익 분산은 크게 줄지만 헤지 비용이 스프레드 수익을 잠식한다.
이 트레이드오프 곡선이 ETF LP 면접에서 직접 쓸 수 있는 소재.
